# Upstream architecture review: Exa MCP and Scrapy

Implementation update: bounded collection scheduling, compact MCP progress, optional host-supplied Exa leads and checkpoint storage are now implemented. See [current behavior and limits](CRAWLER_IMPROVEMENTS.md). The comparison below records the pre-change inspection.

Reviewed 2026-10-13. This is a source and documentation review, not an integration or a live performance test. The linked upstream source was read at the repositories' moving `main`/`master` branches; a commit SHA could not be obtained through the read-only browser, so the links are **not immutable permalinks**. Recheck them before implementation. No paid service was activated.

## What each project does

| Project | Actual role | Relevant structure | Boundary for SourceLedger |
| --- | --- | --- | --- |
| [Exa MCP server](https://github.com/exa-labs/exa-mcp-server) | MCP adapter for Exa's hosted web search/content services; **not an AI language model**. | [`mcp-handler.ts`](https://github.com/exa-labs/exa-mcp-server/blob/main/src/mcp-handler.ts) registers tools according to [`toolRegistry.ts`](https://github.com/exa-labs/exa-mcp-server/blob/main/src/toolRegistry.ts). [`webSearch.ts`](https://github.com/exa-labs/exa-mcp-server/blob/main/src/tools/webSearch.ts) performs search with highlights; [`webFetch.ts`](https://github.com/exa-labs/exa-mcp-server/blob/main/src/tools/webFetch.ts) accepts multiple URLs, calls the hosted `/contents` service, applies retry/timeout, and formats text plus per-URL errors. | Useful as an optional source-discovery or fallback fetch provider. Search results and Exa-rendered text remain candidates/evidence awaiting SourceLedger verification, never verified prices by themselves. |
| [Scrapy](https://github.com/scrapy/scrapy) | Python crawling framework; **not an AI language model**. | [Engine](https://github.com/scrapy/scrapy/blob/master/scrapy/core/engine.py) coordinates requests, [scheduler](https://github.com/scrapy/scrapy/blob/master/scrapy/core/scheduler.py) queues them, downloader/middleware fetches, spiders parse, item pipelines persist. ### Exa details verified in source

- Default advertised tools are `web_search_exa` and `web_fetch_exa`. `web_search_advanced_exa` and `agent_run` are optional. The registry gates `agent_run` through a `requiresUserProvidedApiKey` flag; hosted documentation also describes OAuth access, so that internal flag should not be read as excluding hosted OAuth. [README](https://github.com/exa-labs/exa-mcp-server#available-tools), [registry](https://github.com/exa-labs/exa-mcp-server/blob/main/src/toolRegistry.ts).
- `web_fetch_exa` accepts an array of URLs and `maxCharacters` per page (default 3,000). It reports errors for individual URLs. This is a useful **tool-call batching pattern**, but truncation can omit a price or condition, and formatted Markdown may not preserve DOM context. It does not demonstrate that one paid request covers a whole site or that the service bypasses blocked pages. [Source](https://github.com/exa-labs/exa-mcp-server/blob/main/src/tools/webFetch.ts).
- `web_search_exa` accepts a natural-language query and returns highlights. The source explicitly suggests fetching selected URLs when highlights are insufficient. Search highlights are therefore discovery material. [Source](https://github.com/exa-labs/exa-mcp-server/blob/main/src/tools/webSearch.ts).
- The hosted MCP endpoint is `https://mcp.exa.ai/mcp`. [Exa's documentation](https://exa.ai/docs/get-started/exa-mcp) states anonymous startup is possible; [the repository](https://github.com/exa-labs/exa-mcp-server#authentication) states rate limits and OAuth/API-key paths. A Codex or Claude **subscription does not imply Exa's hosted service is included without limits or cost**. Do not enable it by default or silently select a paid path.

### Scrapy details verified in source/docs

- The scheduler separates enqueued requests from completed requests. Scrapy's [resume guide](https://docs.scrapy.org/en/latest/topics/jobs.html) stores the queue and duplicate filter in a per-job `JOBDIR`; it warns that unclean termination can corrupt that job directory. [Scheduler source](https://github.com/scrapy/scrapy/blob/master/scrapy/core/scheduler.py).
- [Request fingerprints](https://docs.scrapy.org/en/latest/topics/request-response.html#request-fingerprints) account for request semantics beyond a simple URL string. SourceLedger should preserve query/form state and page section in task identity where those change product results.
- [Per-domain concurrency](https://docs.scrapy.org/en/latest/topics/settings.html#concurrent-requests-per-domain) and [AutoThrottle](https://docs.scrapy.org/en/latest/topics/autothrottle.html) provide a model for backpressure. Effective request rate must respond to latency, 429, and server errors; merely raising parallel workers is not a general speed improvement.
- [Downloader middleware](https://docs.scrapy.org/en/latest/topics/downloader-middleware.html) separates transport concerns from parsing. SourceLedger already has HTTP/Playwright backends; reuse this separation instead of requiring Twisted/Scrapy for every user.

## Current SourceLedger comparison

| Concern | SourceLedger code observed | Gap / opportunity |
| --- | --- | --- |
| Search | [`search.py`](../su_crawler/search.py) uses opt-in SearXNG, bounds results, rejects unsafe URLs, and writes candidates without prices. | Add Exa only as an **explicit optional provider** after checking terms, limits, privacy and cost; keep candidate provenance and approved URL selection. A connected AI app can use its own web tool without requiring this integration. |
| Scope and extraction | [`catalog_collection.py`](../su_crawler/catalog_collection.py) requires a confirmed plan, selected URLs, filters/conditions, adapter or JSON-LD extraction, and page-level coverage. [`pipeline.py`](../su_crawler/pipeline.py) stores source evidence and validates observations. | Preserve these safeguards. Exa text alone should not promote an offer to verified; retain original URL, fetch time, field-level quote/locator, conditions and evidence artifact. |
| Crawl queue/checkpoint | `catalog_collection.py` uses `deque`, `queued`, `visited`, a scope/budget binding and SQLite [`catalog_checkpoint.py`](../su_crawler/catalog_checkpoint.py). A page is recorded as in-flight before fetch. | For concurrent work, persist **per-URL states** (`queued`, `leased`, `completed`, `review`, `failed`), lease expiry and attempt count. Recover interrupted leases without duplicating committed observations. Keep the approved URL set and budget binding immutable. |
| Parallelism and rate control | The inspected `collect_plan` loop dispatches pages serially. Higher-level job handling in [`assistant_runtime.py`](../su_crawler/assistant_runtime.py) is asynchronous from the MCP caller, but its worker does not make this loop concurrent. (Other concurrent paths may exist outside this inspected loop.) | Add bounded concurrency in the collection engine, with per-host cap and delay; use one SQLite writer or transactional merge. Parallelism should be an explicit plan setting that the model reports before execution. |
| MCP output | [`mcp_server.py`](../su_crawler/mcp_server.py) exposes start/status/paged observations for a lower-level collection path; assistant jobs also use submit/status/results. | Return compact progress and counts by status with stable pagination/cursors. Avoid sending every page's full evidence to the AI context or forcing model re-entry for each URL. Exa's multi-URL input is a useful interface pattern, but retain per-URL receipts. |

## Recommended changes, in order

1. **Plan disclosure before collection.** Display the selected AI model(s), execution mode, approved sites/sections, URL count if known, page/time budget, checkpoint status, and what evidence will count as verified. Recommend Codex Sol and Claude Opus for their respective connected subscription apps; do not imply both can run simultaneously from a single app. Let the user alter model/site selection in the plan. This is independent of Exa and Scrapy.
2. **Durable bounded parallel queue.** Move each approved URL to a transactional task row with stable request identity (including section/query state), lease, retry class, status, timestamps, and provenance. Keep a hard per-host cap, initial low concurrency and adaptive cooldown on 429/5xx. Browser fallback has its own lower cap. Make completion idempotent and preserve existing field-level evidence. Benchmark against the same frozen URL list with checkpoint on.
3. **Compact MCP progress.** Offer a single start operation and status/summary/pages endpoints. Summaries should include total/queued/running/completed/review/failed, elapsed time, per-host backoff, and a final report path. Paged rows expose complete evidence only on demand. This can reduce model tokens independently of network time.
4. **Optional Exa evaluation.** If users opt in, test search recall and blocked-page fetches on a small approved sample, recording service cost/limits, URL and field coverage, changed content, and evidence fidelity. Do not rely on Exa to supply missing prices or claim site-wide completeness from search results. The existing offline path must remain available.

Acceptance criteria for (2): identical frozen URL/section scope; no missing/duplicate URL tasks after clean resume or hard interruption; no unapproved domain; price and commercial-condition parity or explicit review differences; evidence hashes intact; sequential/parallel elapsed times recorded over repeated runs. Real subscription-app end-to-end timing and tokens require separate model-side instrumentation and should not be inferred from crawler timings.

**Limits of this review:** upstream code and official docs were inspected, but Exa MCP was not connected and Scrapy was not installed or benchmarked. Cost, blocked-page success, integration effort, and speedup are unmeasured. These are architecture recommendations, not verified performance claims.
