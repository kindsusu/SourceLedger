## 결론

제트카 화물차만 수정해서는 다른 사이트의 누락을 막을 수 없다. **작업 종료, 상품 발견 범위, 가격·옵션 추출 범위, 개별 값의 검증 상태를 분리**해야 한다. 전체 상품 수나 목록의 끝을 입증할 수 없는 사이트는 `전체 완료`가 아니라 `범위 확인 불가`로 표시해야 한다.

임의의 모든 사이트에서 누락이 절대 없다고 보장할 수는 없다. 대신 누락·미지원 구조·탐색 한계가 있는데도 완전 수집으로 판단하는 일을 막고, 확인되지 않은 부분을 후속 검토로 넘기는 것이 목표다.

검토 범위는 상품 발견, 사이트별·일반 추출, 근거 검증, 체크포인트, 병렬 처리, 결과표, XLSX, 배치·MCP·UI 집계다. 모든 외부 사이트의 실수집이나 보안 전수 검증을 수행했다는 의미는 아니다. 기존 미커밋 최적화 변경은 보존했다.

## 기존 검증에서 정정할 사항

- 제트카 화물차 3페이지에는 각각 계약기간별 가격 5행이 있었다. 기존 추출은 주소를 인식하지 못해 JSON-LD 대표 가격 1행씩만 저장했다. 저장 HTML에서 주소 인식만 임시 보정하자 총 15행이 추출됐다. 누락은 12행이다.
- 따라서 기존 20 URL·169행 결과는 완전성의 정답으로 쓸 수 없다. 이 12행만 추가하면 당시 원본 기준 181행이다. 단독 수집 187행에는 배너 가격·보증금·취소선 가격 등 별도 유형 6행도 포함돼 있다.
- Sol 표본의 요청→최종 답변은 재사용 끔·브라우저 1개 235.93초, 재사용 켬·1개 166.18초, 재사용 켬·2개 139.04초였다. 첫 두 설정 사이에는 스케줄러 변경도 포함됐다. 모두 같은 누락을 포함한 1회 실행이므로 완전 수집의 속도 개선이나 보편적 모델 순위로 해석하면 안 된다.
- Sol 단독 수집은 1,312.61초·187행이었지만 추가 상호작용과 가격 유형을 포함했고, 4페이지를 미완료로 표시했다. 소스레저 자체의 처리 비용만 비교하는 동일 조건 실험은 아니다.

## 사이트 공통 설계

먼저 승인 범위를 고정 URL 목록, 카테고리, 사이트 전체 중 무엇으로 볼지 구분한다. URL 수, 고유 상품 수, 옵션 수, 가격조건 수, 관측 행 수를 혼용하지 않는다.

페이지·구역마다 발견 수/예상 수와 근거, 표시된 항목, 추출된 식별자, 명시적 제외, 미해석 항목, 미방문 탭·필터·옵션, 한도·실패 이유, 원본 참조를 남긴다. 알 수 없는 예상 수는 0이 아니라 빈 값으로 유지한다. 건수만 같다고 통과시키지 않고 상품·옵션·조건의 집합을 대조한다. 파싱 실패 행, 같은 가격의 다른 옵션, 가격 문의 상품도 단순히 비교 대상에서 사라져서는 안 된다.

- **작업 상태:** 대기, 실행, 종료, 중단.
- **범위 상태:** 근거가 있는 범위 내 완료, 부분 수집, 확인 불가, 제외.
- **값의 상태:** 검증됨, 검토 필요, 가격 미공개, 충돌.

범위가 완료돼도 미공개 가격이나 비교 불가능한 조건은 남을 수 있다. `가격 문의`는 원문 조건을 수집한 것이며 가격을 추정할 이유가 아니다. 승인 목록을 모두 방문한 것도 사이트 전체 상품을 찾았다는 뜻은 아니다.

새 사이트는 목록·상세·옵션 구조를 확인하고 제안된 추출 규칙을 표본에서 검증한 뒤 확대한다. 모르는 구조는 연결된 AI와 브라우저가 보완하되, 이미 검증된 페이지마다 AI가 다시 해석하지 않도록 한다. 화면에 확인되지 않은 옵션 조합을 만들지 않는다.

## 실행 순서와 통과 기준

1. 공통 범위 판정과 `확인 불가` 집계를 구현하고 MCP·UI·XLSX에 전달한다. 이전 169행 기준을 완전성의 정답에서 제외한다.
2. 제트카 경로, 공통 JSON-LD 파서, 옵션 결과 표시를 수정한다. 식료품·의류·부품·렌트 등 서로 다른 구조의 고정 테스트를 추가한다.
3. 체크포인트에 규칙 버전을 적용하고 저장 원본 재분석을 구현한다. 규칙 변경·중단·증거 손상·중복 요청을 검증한다.
4. 수집기와 독립적으로 정답을 지정한 원본 묶음에서 상품·옵션·조건별 결과를 대조한다. SQLite→MCP→UI→XLSX까지 식별자·값·근거 해시가 보존되는지 확인한다.
5. 저장·스케줄링·정책 캐시를 최적화한다. 승인 목록, 새 체크포인트, 증거 요구사항, 요청한 구독 모델을 같게 두고 동시성 1과 2를 비교한다. 모델 API는 사용하지 않는다.
6. 그다음 요청된 실제 사이트를 검증한다. 요청→최종 정리, 목록 발견, 브라우저/네트워크, 추출, 체크포인트, 보고서, 검수 시간과 재시도·용량·제공되는 토큰 사용량을 기록한다. 시간 비교는 반복 측정하고 사이트 변경을 분리한다.

누락이 늘어난 실행은 더 빨라도 개선으로 인정하지 않는다. 사이트 전체 완료는 목록 끝과 옵션 범위를 입증했을 때만 표현한다.

## 회귀 테스트

명령: `.venv/Scripts/python.exe -m pytest tests -q`.
