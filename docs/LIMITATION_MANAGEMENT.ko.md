# 수집 한계와 재처리 관리

[English](LIMITATION_MANAGEMENT.md)

페이지 방문·검토한 옵션의 순회·가격 검증을 구분한다. 하나가 완료됐다고 사이트 전체가 완료된 것은 아니다.

## 검토한 수집 규칙

MCP `update_research_plan` 또는 웹 UI의 고급 수집 규칙에서 `collection_rules`를 설정한다. 계획에 등록한 정확한 URL별로 조작 절차(`recipe`), 필드 선택자(`selectors`), 상품 행 선택자(`row_selector`), 필요한 경우 워크스페이스 내부의 기존 로그인 프로필(`profile_dir`)을 지정한다. 변경하면 기존 승인이 해제되므로 수정된 실행 계획을 확인하고 승인한다. 수집기 자체는 모델·유료 API를 호출하지 않는다. 키는 정확한 후보 URL이거나, 후보 하나 이상과 맞는 `site:<호스트>/<경로 패턴>`이다. 정확한 URL 규칙이 패턴보다 우선하고, 패턴끼리는 더 구체적인 쪽이 적용된다.

호스트 어시스턴트가 제안한 규칙에는 `"origin": "proposed"`가 붙는다.
- **안전 검사:** 입력, 로그인 프로필, 구매·로그인·제출·구독 조작을 할 수 없다.
- **페이지 정보:** `prepare_rule_proposal`이 후보 페이지 하나를 캡처해 구조 개요, 조작 요소, 범용 추출 결과를 돌려준다.
- **시범 실행:** `trial_collection_rule`이 규칙을 한 번 실행해 결과를 새 계획 개정에 기록한다. 가격이 있는 행이 나오고, 저장한 근거를 다시 추출해도 같은 행이 나오고, 화면이 정착했고, 접근 차단이 없어야 통과한다.
- **수집:** 통과한 개정을 사용자가 승인한 뒤에만 수집에 쓰인다. 수집할 때마다 시범 실행 영수증을 다시 확인하고, 시범 실행 뒤에 바뀐 규칙은 보류한다(`held_rules`).

- 옵션 선택은 상위 옵션을 바꾼 뒤 하위 목록을 다시 읽는다. 가격 갱신 완료를 뜻하는 실제 화면 신호를 수집 규칙에 지정한다.
- 페이지 이동은 다음 버튼과 페이지 상한을 지정한다. 더보기·스크롤도 확인한 화면 요소를 기준으로 실행한다.
- 상태별 HTML·선택 라벨·수집 시각·원본 해시를 따로 저장하고 가격 행과 연결한다.
- 순회 한도·지원하지 않는 컨트롤·멈춘 목록은 부분 수집 또는 확인 불가로 남긴다. 항목 수가 잠시 변하지 않는다는 이유만으로 전체 완료 처리하지 않는다.

규칙 예시는 영문 문서에 있다. CSS 선택자와 완료 신호는 실제 사이트에서 확인해야 한다. 없는 통화나 계약 조건을 규칙으로 만들어 넣지 않는다.

`scroll_list`는 항목이 누적되는 목록과 명시적인 종료 표시를 지원하며, 목록 교체·가상 스크롤은 부분 수집으로 남긴다. `enumerate_buttons`는 `data-value`가 있는 제출용이 아닌 버튼 그룹 하나를 지원한다. 페이지 이동 전 캡처에 있는 링크도 같은 호스트의 탐색 대상으로 유지한다. 선택 상태 수는 고유 상품 수와 다르다. 준비 표시가 보인다는 사실만으로 비동기 가격 갱신을 확정할 수 없으므로 옵션 후보는 검토 표시를 유지한다.

`enumerate_options`와 `enumerate_buttons`에는 선택 항목 `price_selector`를 지정할 수 있다. 필드 선택자가 읽는 견적 가격 요소를 가리킨다. 수집기는 옵션을 선택할 때마다 그 요소의 화면 텍스트를 선택 직전 값(하위 옵션은 상위 옵션 선택 후의 값)과 비교하고, 추적 중인 네트워크와 텍스트가 잠잠해질 때까지 기다린다.

- `changed`: 가격 텍스트가 바뀐 뒤 안정됐다. 후보에 가격 갱신 검토 표시를 붙이지 않는다.
- `identical_after_quiet`: 추가 대기 후에도 텍스트가 같다. 두 옵션의 가격이 같거나 화면이 갱신되지 않았을 수 있으므로 `identical_amounts_after_network_quiet_review` 검토 표시를 붙인다.
- 그 밖의 결과(`no_price_displayed`, `untracked`, `timeout`): `selection_price_settlement_unconfirmed` 검토 표시를 유지한다.

캡처마다 `price_settlement`(결과·선택자·텍스트 해시)를 저장하고 단계 추적 기록에 결과별 건수를 남긴다. `price_selector`가 없으면 기존 동작과 같고 옵션 후보는 모두 `selection_price_settlement_unconfirmed`를 유지한다.

## 접근과 재처리

1. **인증:** 권한 있는 기존 로컬 프로필을 명시적으로 사용한다. 비밀번호를 자동 취득하거나 접근 제한을 우회하지 않는다. 프로필은 Git에 포함하지 않는다.
2. **브라우저 인계:** 연결된 Codex·Claude가 승인된 미해결 URL을 직접 열고 `submit_browser_evidence`로 원문을 제출할 수 있다. 제출값은 검토 상태로 남는다. SourceLedger가 AI 앱의 브라우저를 자동 제어하는 기능은 아니다.
3. **문제 원장:** `get_collection_issues`로 원인·근거·다음 조치·시도 횟수를 확인하고, `triage_collection_issue`로 검토 상태를 관리한다. 관련 근거나 이후 검증 실행 없이 해결 처리하지 않으며, 이슈 상태 변경이 과거 가격·범위를 검증 완료로 바꾸지 않는다.
   범위 문제를 해결하려면 `status: "resolved"`와 `evidence: {"kind":"revalidated_run","reference":"<이후 실행 ID>"}`를 전달한다. 이후 실행은 같은 URL·소스·어댑터(일반 선택자에서는 어댑터 없음)에서 같은 구역을 완료해야 한다. 옵션 문제는 해당 구역에 옵션 위치값도 있어야 한다. 레시피나 확정 계획 지문이 바뀌었다면 `scope_revision`에 검토 사유와 변경 전후 지문을 명시한다. 예: `{"reason":"검토한 수정 사유","changed":{"recipe_fingerprint":{"from":"기존 지문","to":"새 지문"}}}`. 계획 지문도 바뀌었으면 `changed.plan_fingerprint`를 함께 넣는다. 값은 두 실행의 저장 기록과 정확히 일치해야 한다.
4. **재시도:** 일시적인 실패에만 제한된 예산을 부여한다. 인증·정책 문제는 선행 조치가 필요하고 재시도 체인에는 상한이 있다. 같은 작업을 재개해도 사용한 예산은 초기화되지 않는다.
5. **구조 변경:** 이전의 비교 가능한 구역이 사라지거나 인식되지 않으면 검토 대상으로 남긴다. 상품이 실제로 삭제됐다고 추정하지 않는다. 추출 규칙 수정은 저장 원본 재분석으로, 최신 가격 확인은 새 수집으로 구분한다.

브라우저 자체 실행은 `source-ledger doctor --verify-browser-launch --browser-display-mode headless` 또는 `visible`로 별도 진단한다. 요청한 표시 모드를 몰래 바꾸지 않는다.

UI의 수집 문제 목록과 XLSX **Collection Issues** 시트에서 미해결 항목을 볼 수 있다. 상태 변경은 이 시트만 갱신하고 과거 범위 기록은 유지한다. Excel에서 보고서를 열어 갱신이 막히면 응답에 `report_refresh: "pending"`가 표시된다. DB 상태는 이미 저장됐으므로 파일을 닫은 뒤 같은 상태 변경을 다시 실행해 시트를 갱신할 수 있다. SQLite가 기준 원장이며 CSV·ERP 연동은 추가하지 않는다.
