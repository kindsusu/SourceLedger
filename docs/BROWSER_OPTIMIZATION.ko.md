# 브라우저 재사용·동시성 최적화

가격 근거·더보기 완료 판정·승인 범위·체크포인트를 유지하면서 반복 실행 비용과 페이지 대기를 줄인다.
SQLite 기록은 조정 담당 한 곳에서 수행하고 Playwright 동기 객체는 스레드 사이에 공유하지 않는다.

초기 구현은 `browser_reuse`, `browser_concurrency`를 명시적으로 설정해 비교한다.
기존 호출은 재사용 끔·브라우저 1개를 유지한다. 브라우저 동시성은 전체 동시성 이하여야 하며,
HTTP와 브라우저가 전체·사이트별 제한과 요청 간격을 공유한다.

브라우저 작업자마다 자기 Playwright·Chromium을 소유하고 URL마다 새 컨텍스트를 생성한다.
캡처 후 컨텍스트·라우트·리스너를 정리한다. 로그인 프로필은 일반 풀에서 제외한다.
우선 한 배치 안에서 재사용하고, 배치 사이 재사용은 별도 실험으로 둔다.

## 외부 코드 검토

- [Crawlee BrowserPool](https://github.com/apify/crawlee-python/blob/master/src/crawlee/browsers/_browser_pool.py): 여유 브라우저 재사용, 수명 관리와 종료.
- [scrapy-playwright](https://github.com/scrapy-plugins/scrapy-playwright/blob/main/scrapy_playwright/handler.py): 페이지·컨텍스트 제한, 시작 잠금, 실패 시 자원 반환.
- [Crawl4AI](https://github.com/unclecode/crawl4ai/blob/main/crawl4ai/async_dispatcher.py): 메모리 기반 작업 제한과 사이트별 재시도 대기. 메모리 자동 조절은 후속 후보이다.
- [Scrapy](https://github.com/scrapy/scrapy/blob/master/scrapy/extensions/throttle.py): 빠른 오류 응답으로 가속하지 않는 지연 기반 속도 조절. 후속 조정 후보이다.
- [ego-lite](https://github.com/citrolabs/ego-lite): 작업별 탭 관리와 사용자에게 제어 전달. 공개 도우미는 자체 브라우저 런타임에 의존하며, 검토 시점 README는 macOS 지원·Windows 비공개 베타 예정으로 안내한다. 이번 성능 비교에 도입하지 않는다.

전체 프레임워크를 교체하지 않고 필요한 설계만 참고한다. 유료 서비스나 모델 API를 추가하지 않는다.

## 검증 순서

1. 기존 제트카·공카 525 URL에서 대표 목록을 고정한다. 제트카 신차·중고·화물과 공카 장기렌트 더보기·렌트패스·한달·하루 목록 및 상세를 포함한다.
2. Sol 6.1 구독 실행으로 A(재사용 끔·브라우저 1), B(재사용 켬·1), C(재사용 켬·2)를 비교한다. 전체 동시성 2, URL 순서, 20 URL 배치, 600초 제한, 새 체크포인트와 증거 기준을 유지한다. 실수집끼리는 동시에 실행하지 않는다.
3. URL·섹션 누락, 가격·통화·계약조건, 원본 증거를 검증한다. 실제 사이트 변경은 원문으로 분리하며 과거 값에 맞추지 않는다.
4. 사용 가능한 정확한 구독 모델로 같은 대표 목록과 가장 적합한 수집 설정을 비교한다. 미지원 모델은 대체하거나 API로 실행하지 않는다.
5. 대표 검증을 통과하면 명시적으로 요청한 Sol 6.1과 표본에서 가장 빨랐던 Claude Haiku 5.5로 전체 고정 목록을 검증한다. 표본의 순위만으로 전체 사이트 성능을 단정하지 않는다.

요청부터 최종 답변까지, 수집 실제 경과 시간, 작업자 누적 시간, 브라우저 실행·재시작 횟수,
실제 동시성, 실패·재시도, 증거 용량, CLI가 제공하는 토큰을 기록한다. 미제공 사용량은 추정하지 않는다.
누락이 있는 실행은 더 빨라도 개선으로 인정하지 않는다. 실수집 결과는 로컬 벤치마크 폴더에 보관하며 Git에 넣지 않는다.

A와 B 사이에는 완료 순서로 처리하는 스케줄러 변경도 포함된다. 따라서 재사용 단독 효과라고 표현하지 않는다. B와 C는 같은 스케줄러에서 브라우저 동시성만 비교한다.

## 대표 목록 실측 결과 (2026-10-13)

대표 20 URL은 이전 525 URL의 부분집합이다. 제트카 신차 4·중고 4·화물 3,
공카 상품군 목록 4·한달 상세 3·하루 상세 2개를 포함한다. 목록 SHA256은
`a33c233cc54dfd1bad1af6848f91165f1fbc9982767d8ca846d1bd87b07cc720`이다.
모든 실행은 새 체크포인트, 승인된 서버 배치 1개, 600초 제한, 전체 동시성 2,
동일한 증거 조건으로 순차 진행했다.

요청부터 최종 답변까지 A→B는 29.6%, B→C는 16.3%, A→C는 41.1% 짧았다.
A→B에는 완료 순서 스케줄러 변경도 포함돼 브라우저 재사용만의 효과로
볼 수 없다. 브라우저 시작 시간 합계는 각각 5.03·0.64·0.47초였다.
나머지 수집 경과 단축에는 처리 순서와 대기 시간 중첩이 포함된다.
세 실행 모두 169개 관측 행을 기록했고, 이전 대표 목록과 비교해 URL 누락,
가격·통화 및 상품 조건 관측 차이, 증거·체크포인트 감사 오류가 없었다.

각각 한 번의 실제 실행이므로 안정적인 모델 순위로 해석하면 안 된다.
Sonnet 실행의 수집 시간이 긴 구간에는 페이지 탐색 59.89초, 증거 확보
67.22초가 포함됐다(다른 C 실행은 각 구간 대체로 13~17초). 이 기록만으로
모델이 수집기를 느리게 했다고 판단할 수 없다. 서버가 승인된 배치를
수행하므로 모델 차이는 주로 설정·도구 사용·최종 검토에, 수집 시간은
실시간 사이트·네트워크 상태에도 영향을 받는다. Claude 결과 메타데이터와
메시지는 Opus·Sonnet·Haiku 5.5의 실제 모델 ID가 요청과 일치함을 확인했다.
Codex는 Sol/Luna의 명시적 `-m` 선택을 기록했지만 이벤트에 별도 백엔드
모델 ID가 나오지 않았다. 두 CLI 모두 구독 인증을 사용했고 모델 API는
호출하지 않았다. 최고 메모리는 기록되지 않아 추정하지 않는다.

설정 C의 전체 525 URL 실행 및 직전 Sol 6.1 서버 배치 기준(31분 34.87초)과의
비교는 진행 중이다. 전체 목록 SHA256은
`01fe8e7fc585cc0d5292b0cf030befcf000b421c6ee5c16ec9419eee98faa8d7`이다.
대표 결과만으로 두 사이트 전체 목록의 완전성이나 전체 시간 단축을 주장하지 않는다.
