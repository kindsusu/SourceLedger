# 체크포인트 저장 최적화

체크포인트 형식은 2026-10-13 구현·측정했습니다. SQLite 원장과 XLSX 보고서 형식을 유지하며, 해당 측정에서 기존 원본 증거와 조사 결과는 수정하지 않았습니다.

## 달라진 동작

새 체크포인트는 HTML·스크린샷 바이트를 SHA-256별로 `checkpoint_blobs/`에 한 번 저장하고, SQLite에는 참조만 기록합니다. 압축 효과가 있는 본문은 무손실 gzip을 적용하며, 이미 압축된 이미지는 재압축하지 않습니다. 파일 저장을 마친 뒤 DB를 갱신하므로 저장 실패 시 이전 체크포인트는 유지됩니다. 중단된 저장에서 사용하지 않는 파일이 남을 수 있으며, 아래의 제한적인 보관 정책으로 정리합니다.

복원 시 크기·해시를 검증하며, 누락·손상이 있으면 재개를 중단합니다. 기존 base64 체크포인트도 읽을 수 있습니다. 가격·수집 범위·시간 및 페이지 예산·복구 상태를 유지합니다. 병렬 스케줄러를 추가하는 변경은 아닙니다.

**백업·이동할 때 DB뿐 아니라 `checkpoint_blobs/`, `evidence/`를 포함한 출력 폴더 전체를 보관해야 합니다.** 이전 프로그램 버전은 새 참조 형식을 읽지 못합니다. 기존 DB는 자동으로 축소되지 않으며, 이전 행을 갱신해도 SQLite의 빈 공간이 남을 수 있습니다. 수집 중 파일 삭제나 DB 축소 작업은 하지 않습니다.

## 실측 결과

제트카·공카 525개 URL, 체크포인트 27개의 기존 데이터를 네트워크 없이 복사본에서 재생했습니다. 원본은 읽기 전용으로 열었고 변경하지 않았습니다. 복원된 체크포인트 27개가 기존 상태와 완전히 같았습니다. 복사 DB에만 VACUUM을 적용하고 모든 연결을 닫아 임시 WAL/SHM을 제외한 용량을 측정했습니다.

| 항목 | 기존 | 개선 후 |
| --- | ---: | ---: |
| DB 및 새 체크포인트 파일 | 882.27MB | 556.94MB |
| 증거·엑셀·로그를 유지한 전체 보관량 환산 | 1,522.55MB | 1,197.21MB |
| 체크포인트 반복 저장 시간 — 3회 중앙값 | 17.72초 | 4.39초 |

전체 보관량 기준 **325.34MB, 21.37% 감소**입니다. 원본 증거 628.63MB는 그대로 유지합니다. 개선 후 전체 용량은 실측한 복사 DB·체크포인트 용량을 기존 실행 데이터에 대입한 값이며, 새 사이트 수집이나 원본 데이터의 마이그레이션 결과는 아닙니다. MB는 1,000,000바이트 기준입니다.

시간은 동일한 20페이지의 저장 데이터를 1페이지부터 누적하며 단계당 2회, 총 40회 저장한 실험입니다. 새 로컬 폴더를 사용해 기존→개선 순서로 3회씩 측정했습니다. **체크포인트 저장 구간은 75.22% 단축**됐지만 전체 크롤링·네트워크·AI·보고서 작성 시간을 의미하지 않습니다. 전체 수집 속도가 같은 비율로 빨라진다고 볼 수 없으며, 메모리에는 여전히 복원된 캡처를 보유합니다.

검증: 저장·복구·후속 수집 관련 테스트 16개 통과, 실제 체크포인트 27개 복원 일치. 상세 실측은 Git 제외 경로 `.tmp/checkpoint-storage-20261013-115124/result.json`에 보관했습니다.

## 보관 및 정리 정책

최종 결과는 XLSX, 누적 기록은 SQLite에 보관합니다. 결과의 검증·재생성에 필요한 HTML 원문·스크린샷·수집 영수증 등은 디스크에 유지합니다. 새로 저장하는 동일한 원문과 PNG 스크린샷은 `evidence/`에서 SHA-256 기준 파일 하나를 공유하며, 수집별 영수증은 별도로 남습니다. 과거에 쌓인 폴더를 자동으로 합치지는 않습니다. 실제로 새롭거나 바뀐 페이지를 수집하면 저장량은 계속 늘 수 있습니다.

정리 명령은 **기존 출력 폴더 하나**를 대상으로 합니다. 먼저 삭제 없는 미리보기를 실행합니다.

```powershell
python -m su_crawler storage --output-dir "E:\path\to\one-output-directory"
```

미리보기에서 참조하지 않는 체크포인트 내부 자료를 확인했다면 적용합니다.

```powershell
python -m su_crawler storage --output-dir "E:\path\to\one-output-directory" --apply
```

저장된 모든 체크포인트가 참조하지 않는 내부 페이지·파일만 정리 대상입니다. 미완성 `.pending-` 파일은 기본 7일이 지나야 대상이 되며 `--grace-days`는 1~365일 범위에서 바꿀 수 있습니다. 체크포인트 본체, SQLite 관측 기록, 엑셀, 원본 증거, 스크린샷, 수집 영수증, 작업 기록, 조사 워크스페이스는 삭제하지 않습니다. 디스크 총량 제한이나 기간별 증거 삭제, 폴더 이동 후 경로 자동 복구는 포함하지 않습니다. 참조 무결성 오류나 동시 저장 작업이 있으면 안전을 위해 정리를 중단합니다. 수동 정리나 이동 전에는 출력 폴더 전체를 백업하세요.

완료 결과가 포함된 체크포인트를 저장한 뒤 기본적으로 최대 24시간에 한 번 동일한 제한적 정리를 실행합니다. 출력 폴더의 `storage-policy.json`으로 설정할 수 있습니다.

```json
{"automatic_cleanup": true, "grace_days": 7, "maintenance_interval_hours": 24}
```

자동 정리를 끄려면 `automatic_cleanup`을 `false`로 설정하세요. 최근 처리 상태는 `.checkpoint-maintenance/status.json`에 기록하며 정리 실패로 수집 자체가 실패하지는 않습니다. 기본 정책은 증거·오래된 보고서를 삭제하지 않습니다. 다른 드라이브에 이미 저장한 과거 폴더의 중복은 참조를 확인한 뒤 별도의 1회성 정리로 판단해야 합니다. 위의 2026-10-13 용량·속도 수치는 당시 체크포인트 형식의 측정값이며 이번 보관 정책의 절감 실측치는 아닙니다.
